# 路线图

版本：v2（2026-09-25 对齐实际进展）

## 纪律

**每个阶段的验收标准都是"孩子能不能自己玩下去"，不是"功能做完了"。**

具体做法：每个阶段结束就把 iPad 给孩子，**不做任何解释**，在旁边看。孩子卡在哪、
在哪走神、在哪要求大人帮忙，就是下一阶段的输入。这比任何设计讨论都准。

阶段之间不并行。宁可一个游戏打磨透，不要三个半成品。

---

## 阶段 0 · 地基

搭起来的是"所有游戏共用的东西"，本身没有可玩内容。

- Vite + Vue 3 + TS 骨架，PWA 配置（manifest、图标、Service Worker 离线缓存）
- 游戏模块接口与注册表（`docs/DESIGN.md` 4.2）
- 音频系统：音效播放、语音播放、iOS 首次触摸解锁音频
- 首页大卡片网格（先放占位卡片）
- 结算页骨架、家长入口（原设计长按 3 秒，iPad 实测后改为普通按钮，见 DESIGN.md 第 3 节）
- localStorage 读写、头像选择
- 单元测试环境（给规则引擎用）

**验收**：iPad Safari 打开 → 添加到主屏幕 → 点开是全屏的、断网也能开、点卡片有音效反馈。

---

## 阶段 1 · 翻牌配对　—— ✅ 已上线，孩子已验收通过

第一个真正能玩的游戏。这个阶段的重点不是规则（规则很简单），而是**把动画和音效的质感
定下来**——后面两个游戏会沿用同一套手感。

- 规则引擎 + 单元测试（先写，再接 UI）
- 三档难度（4/6/8 对）
- 单人模式 + 和 AI 轮流模式
- AI：有限记忆窗口
- 翻牌动画、配对庆祝、通关庆祝

**验收（最重要的一次）**：孩子独立打开、独立选难度、独立玩完一局，全程不问大人。
如果这一条不过，先修这里，不要往阶段 2 走。

---

## 阶段 2 · 回合制框架　—— ✅ 已上线（做的是蛇梯棋，后被四子棋替换）

本阶段的目的是验证**多人回合制框架**和**多个 AI 对手同时在场**，这个目的达到了。

- 规则引擎 + 单元测试
- 2-4 人，可配 1-3 个 AI
- "轮到谁"的视觉表达（本阶段的设计难点）

**载体换过一次**：原本做的是蛇梯棋，2026-09-24 **下架**（代码保留，未注册）。
下架原因是用户实测后的判断：**零选择 = 零参与感**。整局只有掷骰子一个动作，
孩子玩过的同类游戏都有操作和决策，这个没有。

替换为 **四子棋**（`docs/DESIGN.md` 5.2b）：有真正的选择（往哪一列丢），
但规则一句话讲得完 —— "选择很容易、代价很小"才是我们要的。

> 蛇梯棋的棋盘和动画将来若做成"大富翁式棋盘 + 每格触发小游戏"还能复用。

**验收**：孩子能和 AI 玩完一局，并且**始终知道什么时候轮到自己**。

---

## 阶段 3 · UNO（完整规则 + 可配置牌组）　—— ✅ 已上线

规则最复杂的一个，放在框架成熟之后。

- **完整规则引擎**（全部牌型）+ 单元测试。不含质疑、不含累计叠加（`docs/DESIGN.md` 5.3）
- **牌组配置**：`enabledCardTypes` 决定发牌时放哪些牌 → L1~L4 四级难度阶梯
- 可出牌高亮放大、不可出牌灰掉禁点（默认开，家长端可关）
- 自动喊 UNO 音效
- AI 出牌策略 + 次优概率降智

**上线时先给 L1（纯数字牌）**，让孩子先把颜色/数字匹配玩熟，再逐级解锁。

**验收**：孩子在 L1 下不需要大人讲解就能玩下去（靠高亮自己摸索出规则）；
之后每解锁一级，观察孩子是否在 1-2 局内适应——**如果某一级明显卡住，就退回上一级多玩一阵，
不要硬推**。这个阶梯是给孩子用的，不是进度条。

---

## 阶段 4 · 按孩子的真实反应打磨　—— 🔄 进行中

**这个阶段刻意不预先列任务。**

前三个阶段会积累一批"孩子实际卡住的地方"，那才是这个阶段的待办事项。现在就把它排满，
等于假装我们已经知道孩子会怎么反应。

**实际做了什么**（2026-09-24 ~ 25，全部来自实测反馈，没有一条是提前规划的）：

- **蛇梯棋下架，四子棋上线** —— 零选择 = 零参与感
- **找相同（Dobble）上线** —— 第四个游戏。目标自明、靠"看"而不靠记忆和策略，
  是四个里孩子**最可能真的赢过大人**的一个
- **一台 iPad 两个人玩**：翻牌配对 / 四子棋 / 找相同都支持。真人用小动物头像、
  电脑用机器人形象区分
- **教学策略定版**：不是每个游戏都要教程，而是**只补"看不出来的那一半"**
  （目标 vs 操作，见 `DESIGN.md` 4.9）。四个游戏的对局页统一右上角 `?`
- **PWA 更新机制**：加到主屏幕后 iOS 不会自己更新，补了设置里的"检查更新"
  + 小红点。**这条链路必须真机验**，浏览器面板里注册不了 Service Worker

**这个阶段的产出不只是功能，还有一批"下次别再犯"的教训**，都记在 `CLAUDE.md`
的「踩过的坑」里 —— 其中好几条（百分比 padding、裸 transform 覆盖定位、
可点区互相压住）都是**只在特定设备上才现形**的那种，值得反复翻。

**下一步**：继续按孩子的反应打磨，**不加新游戏、不做联机**（联机的完整评估见阶段 5+）。

## 阶段 5+ · 多人联机（长期）—— 已评估，**当前决定停在档 0**

评估日期 2026-09-25。**结论：现在不做，继续一台 iPad 轮流玩。**

### 先纠正一个直觉：「面对面多设备」和「联网玩」是同一件事

容易以为面对面会便宜很多 —— 大家在一个房间，走局域网或蓝牙就行。
**但网页应用做不到**：浏览器摸不到局域网发现（没有 mDNS/Bonjour），
Web Bluetooth 不适用于这种场景。绕开服务器只剩 WebRTC，而它**仍然需要一台服务器
帮两边牵线**，还要处理 NAT 穿透，复杂度反而更高。

所以两种玩法都得走服务器中转，差别只有：**怎么找到彼此**、**能容忍多少延迟**。

> **推论：不存在「先做便宜的面对面版，以后再升级联网版」这条省钱路径。**
> 做完前者，后者几乎白送；反过来前者也省不下什么。

### 已经白赚的部分

铁律 3（规则引擎必须纯函数）就是为这一天埋的，回报兑现：

| 项目 | 一般项目要做 | 我们的状态 |
|---|---|---|
| 游戏逻辑能否在服务端跑 | 要重写（逻辑和 UI 缠在一起） | **已经可以，一行不用改** |
| 服务端权威校验 | 要补一套 | `getLegalActions` 已有 |
| 发牌/洗牌能否复现 | 用了 `Math.random` 就对不上 | 随机源在 state 里，天然可复现 |
| 四个游戏要几套网络层 | 每个一套 | **一套**（`GameModule` 接口统一） |

这块通常占联机改造工作量的四到五成，**对我们是零**。

### 真正要新做的（按难度 × 风险排）

| # | 工作 | 量 | 风险 | 说明 |
|---|---|---|---|---|
| 1 | 房间与连接 | 小 | 低 | 已经在 Cloudflare 上，**Durable Objects 天生就是「一房间一对象」**，自带 WebSocket，这个量级基本在免费额度内 |
| 2 | 隐藏信息裁剪 | 中 | 中 | 见下表。错了不会报错，只会悄悄泄密 |
| 3 | **断线重连** | 中偏大 | **高** | **iOS 上 app 切到后台 WebSocket 立刻断**，而孩子一定会锁屏、切出去、走开。没做好就是「每次回来都要重开一局」= 功能不可用 |
| 4 | 「怎么找到彼此」的界面 | 中 | 中 | **这是设计难题不是技术难题**：零阅读依赖前提下，5 岁怎么加入房间？四位数字码她读不出也打不进。备选：三个动物图案当密码 / 扫码 / 家长代劳 |
| 5 | 找相同的实时公平性 | 大 | 高 | 见下 |

**哪些游戏有秘密**（"不渲染" ≠ "看不到"，联机后打开开发者工具就全看见了）：

| 游戏 | 有秘密吗 | 说明 |
|---|---|---|
| 四子棋 | **没有** | 棋盘全公开 |
| 找相同 | **没有** | 三张牌都摊在桌上 |
| 翻牌配对 | 有 | `cards[]` 带着每张牌的图案，包括盖着的 |
| UNO | 有，更严重 | `hands` 是所有人的手牌，`drawPile` 是**整副牌未来的发牌顺序** |

**找相同不联机。** 前三个是回合制，延迟只影响手感；**找相同是抢答，延迟直接决定谁赢** ——
网快的人永远赢，而且看起来像"我明明先点的"。要做对得靠服务端时间戳 + 客户端预测，
是另一个量级的复杂度。这个游戏本来就是为"两个人挤一台 iPad"设计的。

### 微信这条路：成本主要不在技术，在资质

| 门槛 | 说明 |
|---|---|
| 小程序主体 | 个人主体限制多，很多能力要企业主体 |
| **ICP 备案** | 通常要求**中国境内主体 + 境内服务器**。**用户在马来西亚，这是实打实的障碍** |
| 审核 / 合规 | 小程序要过审；公开发布涉及未成年人防沉迷与实名认证（自己孩子玩不涉及） |
| UI 要重写 | 小程序用 WXML/WXSS，界面层得重做 —— **但规则引擎能原样搬过去**（又一次铁律 3 的回报） |

更根本的问题：**微信买到的是「账号身份 + 社交关系链」，而我们不需要。**
场景是"和**认识的**小朋友一起玩"，房间码 + 分享链接就够了；铁律 7 明确不做陌生人社交；
韩国朋友那边微信也用不上。

> **结论：不要为了联机去做微信。** 它解决的问题我们没有，带来的成本我们付不起。

### 两笔容易被忽略的账

- **联机会打破"断网也能玩"。** 现在是纯静态 PWA，加到主屏幕后飞机上都能玩。
  联机后多人模式硬依赖网络和服务器 —— 对一个给孩子的玩具，这是可靠性的实打实下降。
- **联机会引入"会腐坏"的部分。** 现在就算完全停止开发，这个 app 也能一直用下去（一堆静态文件）。
  有了服务器就会腐坏：依赖要升级、账单要付、服务会挂。
  **这是从"一件东西"变成"一项服务"。**

### 三档方案，以及我们在哪一档

| 档 | 做什么 | 状态 |
|---|---|---|
| **0** | **什么都不做，继续一台 iPad 轮流玩** | ✅ **当前就停在这里（2026-09-25 决定）** |
| 1 | 房间码 + Durable Objects，**只支持四子棋** | 未启动 |
| 2 | 加上 UNO（隐藏信息裁剪） | 未启动 |

**为什么档 1 只做四子棋**：零隐藏信息、回合制、节奏慢 —— 用最便宜的方式把
"服务器 + 房间 + 断线重连 + 加入界面"整条链路跑通。真要做联机，这是唯一正确的第一步。
档 2 只在档 1 真的被用起来之后才值得。

### 启动条件（两条都满足才动，现在一条都没满足）

1. 孩子已经稳定地在玩 —— 不是新鲜感，是持续几周主动要玩
2. **孩子自己明确表达了想和小朋友一起玩**

> 第 2 条特别重要：**现在想联机的是大人，不是孩子。**
> 等她自己说出"我想和 XX 一起玩"，那时才知道该做面对面还是远程、该做哪个游戏。
> 提前做等于替她决定她想要什么。

## 旧版本代码的处置

旧 uni-app 版本（登录 / 大厅 / 房间 / 2048 / 完整 UNO）**已连同 git 历史一并删除**
（2026-09-23，用户决定完全重来）。仓库从当前这版重新开始，没有更早的提交。

删之前评估过要不要留：结论是没有保留价值。
- UNO 的规则是公开且标准的，不需要参照一份有 bug 的实现
- 旧代码的规则与 UI 纠缠在一起，恰恰是本次设计要避免的结构（见铁律：规则引擎必须纯函数）
- 需要记住的决策已经写进 `docs/DESIGN.md` 和本文件，不依赖 git 历史

所以：**不存在"迁移旧代码"这个选项**，三个游戏都是从规则引擎开始新写。
